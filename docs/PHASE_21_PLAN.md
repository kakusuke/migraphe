# Phase 21: Plugin Supply Chain Hardening — JitPack 対応 + Lock ファイル方式の SHA-256 ピン留め

> **Status**: PLANNED (not yet implemented)
> **Source**: `~/.claude/plans/maven-central-shiny-tome.md` (planning session 2026-04-28)
> **Scope note**: Maven Central 公開作業 (POM/署名/sources/javadoc/publishing 経路) と CLI 配布は本フェーズの範囲外。別フェーズで扱う。

## Context

Phase 20 で導入された CLI のプラグイン解決機構 (`MavenPluginResolver`) は **Maven Central のみハードコード**、検証は Aether 標準の SHA-1/MD5 のみ、というサプライチェーン的に脆弱な状態にある。

ユーザー目線では、自作プラグインを GitHub にタグ付けするだけで配布できる **JitPack** をカジュアルに使いたいニーズがある一方、JitPack は任意のビルドが走るため、ハッシュ・署名なしのインストールは危険である。

本プランは、**lock ファイル (`migraphe.lock.yaml`) 方式** で JitPack 対応と SHA-256 ピン留め必須化を一体導入する。npm の `package-lock.json` / Cargo の `Cargo.lock` / Bundler の `Gemfile.lock` と同様、人が書く `migraphe.yaml` は宣言的に薄く保ち、解決結果（座標 + リポジトリ + ハッシュ + 推移依存）はツールが lock ファイルに自動生成する。

これにより、

- 利用者は `migraphe.yaml` に座標を書き、`migraphe pin` を 1 回叩くだけで lock ファイルが生成され、安全に導入できる
- lock ファイルをコミットすればチーム全員で一貫性を保てる
- 同一座標の差し替え攻撃・JitPack 側の悪意ビルドは起動時に lock 照合で遮断される
- 推移依存ハッシュも自動収集されるため手書き負担ゼロ

### 確定済みの設計判断
- セキュリティ層は **SHA-256 ピン留め必須** (本体 + 推移依存すべて)
- ピンは **`migraphe.lock.yaml`** に保存。`migraphe.yaml` には書かない
- `migraphe pin` サブコマンドで lock ファイル生成・更新
- **SNAPSHOT もピン可能** (lock 一致なら起動可、不一致ならエラー)
- **エスケープハッチなし**。lock 必須・厳格一本
- リポジトリは **HTTPS のみ受理** (将来 `allow_insecure: true` の拡張ポイントを残す)
- 重複 `id` は拒否
- 認証 (HTTP Basic / Token) と PGP 署名検証は本スコープ外。型に拡張余地は残す

## YAML スキーマ

### `migraphe.yaml` (人が書く・宣言的)

```yaml
repositories:
  # 省略時は maven-central のみ組み込み (id="maven-central")
  - id: jitpack
    url: https://jitpack.io

plugins:
  # 既存の座標文字列形式 (Maven Central から解決)
  - io.github.kakusuke.migraphe:migraphe-plugin-postgresql:0.2.0
  - io.github.kakusuke.migraphe:migraphe-plugin-mysql:0.2.0

  # 追加リポジトリを使うときは Map 形式で repository を明示
  - coordinate: com.github.alice:migraphe-plugin-foo:v1.2.0
    repository: jitpack
```

### `migraphe.lock.yaml` (ツールが生成・コミットする)

```yaml
# This file is auto-generated by `migraphe pin`. DO NOT EDIT.
# Commit this file to lock plugin versions and SHA-256 hashes.
lockfile-version: 1
plugins:
  - coordinate: io.github.kakusuke.migraphe:migraphe-plugin-postgresql:0.2.0
    repository: maven-central
    sha256: 3a7f...e21c
    dependencies:
      - coordinate: org.postgresql:postgresql:42.7.3
        sha256: 8c2e...4b91
      - coordinate: org.checkerframework:checker-qual:3.42.0
        sha256: 1f3a...77ad
  - coordinate: io.github.kakusuke.migraphe:migraphe-plugin-mysql:0.2.0
    repository: maven-central
    sha256: ...
    dependencies: [...]
  - coordinate: com.github.alice:migraphe-plugin-foo:v1.2.0
    repository: jitpack
    sha256: 9e0d...c11f
    dependencies: []
```

## 起動時の挙動

| 状態 | 結果 |
|---|---|
| lock 不在 | エラー: `migraphe.lock.yaml not found. Run 'migraphe pin' to generate it.` |
| lock と `plugins:` が乖離 (座標追加/削除/version 変更) | エラー: `migraphe.lock.yaml is out of sync with migraphe.yaml. Run 'migraphe pin' to update.` |
| lock 内ハッシュと実 JAR が不一致 | `ChecksumMismatchException` (座標 / 期待値 / 実値 / パスを表示) |
| 解決された座標が lock に無い (推移依存の追加など) | `MissingChecksumPinException` (`migraphe pin` を案内) |
| すべて整合 | URLClassLoader 構築 → 通常起動 |

旧形式 (lock 無し・座標文字列のみ) は **DEPRECATED 警告** を出した上で `migraphe.lock.yaml not found` エラーで停止する。

`migraphe pin` 自身は lock を要求しない (生成側のため)。

## 検証フロー

```
                migraphe.yaml + migraphe.lock.yaml
                              |
                              v  PluginConfigPreParser  (yaml: 座標 + 追加パラメータ)
                              v  LockFileReader         (lock: 座標 + sha256 + repo + deps)
                              |
                              v  LockSyncChecker        (yaml と lock の plugins 整合チェック)
                              |     -> 乖離なら LockOutOfSyncException
                              |
                              v  RepositoryRegistry.toRemoteRepositories()
                              |
                              v  MavenPluginResolver.resolveAll(coords, repos)
                              v  -> List<ResolvedArtifact(coordinate, jarPath)>
                              |
                              v  PluginIntegrityVerifier.verify(resolved, lock)
                              |     - JAR ごとに SHA-256 計算
                              |     - lock 内ピンと突合 (mismatch -> ChecksumMismatchException)
                              |     - lock に無い座標が解決されたら MissingChecksumPinException
                              |
                              v  URLClassLoader 構築 -> PluginRegistry.loadFromClassLoader()
```

`migraphe pin` の生成フロー:

```
                migraphe.yaml
                       |
                       v  PluginConfigPreParser
                       v  RepositoryRegistry
                       v  MavenPluginResolver.resolveAll()    -> List<ResolvedArtifact>
                       v  Sha256Calculator.hash(each jar)     -> ハッシュ収集
                       v  LockFileBuilder.build(plugins, deps, hashes, repos)
                       v  LockFileWriter.write(migraphe.lock.yaml)
```

## 実装ステップ (TDD)

各 Step は `/tdd-cycle` で 1〜数周回せる粒度。

### Step 1: `PluginDeclaration` 値オブジェクト
yaml の `plugins:` 1 エントリを表す（座標 + 任意 repository）。
- **Red**: 文字列形式パース / Map 形式パース / 不正な型エラー / 等値性
- **Green**: record `PluginDeclaration(MavenArtifactCoordinate coordinate, Optional<String> repositoryRef)`
- **Refactor**: `Locale.ROOT` / メッセージ整合

### Step 2: `RepositoryConfig` + `RepositoryRegistry`
- **Red**: `mavenCentral()` / `jitpack()` ファクトリ。`http://` 拒否。重複 ID 拒否。`resolve("jitpack")` で取得
- **Green**: record + Aether `RemoteRepository` への変換ヘルパー
- **Refactor**: `MavenPluginResolver.defaultRemoteRepositories` を `RepositoryRegistry.defaults()` に寄せる準備

### Step 3: `PluginConfigPreParser` 拡張
- **Red**: `repositories:` セクション、`plugins:` の 文字列 / Map 両対応、`PluginConfigParseResult(repositories, plugins)` を返す、不正型のエラー UX
- **Green**: 戻り値型変更、ヘルパー (`asString` / `asList` / `asMap`)
- **Refactor**: `PluginConfigPreParserTest` の旧形式テストは「文字列形式エントリ」テストとしてリラベル

### Step 4: `MavenPluginResolver` リポジトリ注入化 + `ResolvedArtifact`
- **Red**: `RepositoryRegistry` 注入 / `resolveAll(coords)` が `List<ResolvedArtifact(coord, path)>` を返す / 座標から repository 指定で適切なリポジトリのみ問い合わせ
- **Green**: シグネチャ変更、`ResolvedArtifact` 新設
- **Refactor**: `defaultRemoteRepositories()` 削除

### Step 5: `Sha256Calculator`
- **Red**: 既知ベクトル (`"hello"` → `2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824`) / 大ファイルでも OOM しない (8KiB チャンク)
- **Green**: `MessageDigest.getInstance("SHA-256")` + ストリーム読み
- **Refactor**: 純粋ユーティリティ

### Step 6: Lock ファイル data model + I/O
- **Red (LockFileTest)**: `LockedPlugin(coordinate, repositoryId, sha256, List<LockedDependency>)` / `LockedDependency(coordinate, sha256)` の等値性とバリデーション
- **Red (LockFileReaderTest)**: 正常な YAML をパース / `lockfile-version` 不一致エラー / 必須フィールド欠如エラー / 不存在ファイルで `Optional.empty()`
- **Red (LockFileWriterTest)**: `LockFile` を YAML として書き出し、ヘッダコメントを含むこと、再パースで等価性
- **Green**: `LockFile`, `LockedPlugin`, `LockedDependency`, `LockFileReader`, `LockFileWriter` 実装。SnakeYAML の `DumperOptions` で安定整形
- **Refactor**: `lockfile-version: 1` 定数化、ヘッダコメント定数化

### Step 7: `LockSyncChecker` (yaml ↔ lock 整合チェック)
- **Red**: `migraphe.yaml.plugins` の座標集合と `lock.plugins` のトップレベル座標集合が一致するかチェック / 不一致時に「追加 / 削除 / 変更」を含むエラーメッセージ / repository 指定の不整合 (yaml で `jitpack` 指定なのに lock では `maven-central`) もエラー
- **Green**: 純粋ロジッククラス
- **Refactor**: メッセージは「`migraphe pin` を実行してください」を必ず含む

### Step 8: `PluginIntegrityVerifier` (lock 参照)
- **Red**: lock の期待ハッシュ Map と `List<ResolvedArtifact>` を突合 / 一致 / mismatch (`ChecksumMismatchException`) / lock に無い座標が解決された (`MissingChecksumPinException`) / 同名異座標
- **Green**: `verify(resolved, lockFile)` 実装
- **Refactor**: 例外メッセージは「座標 / 期待値 / 実値 / パス / 提案アクション」を 1 行で

### Step 9: `PluginResolver` で全部つなぐ
- **Red**: lock 不在 → `LockFileNotFoundException` / lock 乖離 → `LockOutOfSyncException` / lock 一致 → 起動成功 / JAR 改ざん → `ChecksumMismatchException`
- **Green**: `PluginResolver.resolve(baseDir)` の中で `LockFileReader.read` → `LockSyncChecker.check` → `MavenPluginResolver.resolveAll` → `PluginIntegrityVerifier.verify` の順に呼ぶ

## リスクと注意点

1. **破壊的変更**: lock ファイル不在 = 起動失敗。リリースノートに明示し、エラーメッセージで `migraphe pin` を案内する。
2. **SNAPSHOT との両立**: 同一座標で内容が変わる SNAPSHOT は、ピン更新を頻繁に求められる運用負荷が発生する。`migraphe pin` を CI/開発フローの一部に組み込むことで現実的に運用可能。
3. **JitPack 初回ビルド遅延**: JitPack は座標初リクエスト時にビルドを走らせるため、`migraphe pin` 解決が長時間かかる場合がある。失敗時のエラーメッセージに `https://jitpack.io/com/github/<user>/<repo>/<tag>/build.log` の案内を入れる。
4. **HTTPS-only**: 社内 HTTP-only Nexus は当面非対応。将来 `allow_insecure: true` を追加する余地を `RepositoryConfig` に残す。
5. **lock ファイルの並び順**: `migraphe.yaml` の `plugins:` 順を保持する。推移依存は座標の自然順 (groupId, artifactId, version) でソートして diff 安定性を確保。
6. **Aether の SHA-256 非対応**: ローカル解決後の JAR を自前ハッシュするので問題なし。サーバー側 `.sha256` には依存しない。
7. **`migraphe pin --check`**: CI で「lock がコミット忘れ」を検出するための dry-run モード。lock を実ファイルに書かず、生成すべき内容と既存 lock を比較し、差分があれば exit 1。
